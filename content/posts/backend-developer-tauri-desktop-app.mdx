# 백엔드 개발자의 macOS 데스크톱 앱 도전기: Rust와 Tauri v2로 만든 Zenith 개발기

평소에 터미널과 서버, 컨테이너 환경에서만 살던 백엔드 개발자가 최근 처음으로 macOS 데스크톱 앱을 만들어봤습니다.

처음 시작할 때는 "웹뷰 띄우고 스크립트 실행하면 끝나는 거 아닌가?" 싶었는데, 실제로 개발해보니 프로세스 분리, 비동기 IPC, OS 네이티브 창 제어, 그리고 파일 시스템 보안(TOCTOU, 심링크 트랩)까지 파고들어야 할 깊이가 꽤 깊었습니다.
느꼈던 점들, 백엔드 개발자 관점에서 바라본 데스크톱 앱의 구조, 그리고 개발 과정에서 마주친 재미있는 기술적 고민들을 기록으로 남겨보고자 합니다!

## 1. 왜 만들게 되었을까? (만들게 된 계기)

개인적으로 로컬 환경에서 다양한 LLM(Ollama, vLLM)을 띄우거나 AI 코딩 도구(Codex, Antigravity)를 적극적으로 사용하고 있습니다. 그러다 보니 자연스럽게 몇 가지 Pain Point가 생겼습니다.

1. **감당 안 되는 디스크 용량 증발**:  
   사용하지 않는 프로젝트 디렉터리, 도커(Docker) 볼륨, Rust의 `target` 폴더, Node의 `node_modules`, Ollama 로컬 모델, `/tmp`에 생성되는 임시 파일들이 순식간에 수백 MB에서 수십 GB까지 디스크를 잠식했습니다.
2. **흩어져 있는 AI 도구와 모니터링**:  
   구독 중인 여러 AI 도구들의 주간/시간별 사용량 한도를 터미널을 열지 않고도 메뉴바에서 실시간으로 확인하고 싶었습니다.
3. **특정 조건에서의 Mac 슬립 방지 (Keep Awake)**:  
   터미널에서 무거운 백그라운드 작업이나 코딩 에이전트가 긴 시간 작업을 수행 중이고 배터리가 충전 중일 때는 맥북 화면이 잠기더라도 프로세스가 중단되지 않고 끝까지 동작하길 원했습니다.

처음에는 매번 쉘 스크립트를 짜거나 `find`, `rm` 명령어로 직접 지웠습니다. 하지만 매번 수동으로 실행하는 게 귀찮아져서 상용 맥 관리 앱들을 찾아봤습니다. 

그런데 생각보다 가격(구독형)이 비쌌고, 제가 원하지 않는 불필요한 기능까지 잔뜩 들어가 앱이 너무 무겁게 느껴졌습니다. 

> *"내가 원하는 기능만 딱 넣어서, 진짜 가볍고 안전한 네이티브 앱을 직접 만들어보면 어떨까?"*

그렇게 직접 만들기(+ AI의 도움 받기) 프로젝트가 시작되었습니다.

## 2. 기술 스택: Wails와 Electron 대신 Rust + Tauri v2를 선택한 이유

예전에 Go 언어 기반 데스크톱 프레임워크인 **Wails**로 간단한 토이 프로젝트를 만들어본 적이 있습니다. 저는 백엔드 개발자라 Go가 매우 익숙하고 편했지만, 이번에는 **Rust + Tauri v2 + Svelte** 조합을 선택했습니다.

```text
[ Zenith Architecture ]

┌────────────────────────────────────────────────────────┐
│  Frontend UI (Svelte 5 / WebKit WebView)               │
│  - Storage Dashboard, Tray Popup, Charts               │
└───────────────────────────┬────────────────────────────┘
                            │ IPC (invoke, event, channel)
┌───────────────────────────┴────────────────────────────┐
│  Backend Core (Rust / Tauri v2 Core)                   │
│  - tokio 비동기 런타임 (스레드 풀 분리)                │
│  - Safe Cleanup Engine (TOCTOU 방어, Symlink 방어)     │
│  - System Monitoring (sysinfo, Process, Battery)       │
│  - macOS Native APIs (Cocoa / IOKit FFI)               │
└────────────────────────────────────────────────────────┘
```

### 왜 Electron을 고려하지 않았을까?

수많은 데스크톱 앱(Slack, Discord, VS Code 등)이 Electron으로 제작되어 있습니다. 하지만 제가 추구하는 앱의 본질은 **"용량을 청소하고 가볍게 상주하는 시스템 관리 앱"**이었습니다.

일렉트론은 앱마다 독립된 **Chromium 브라우저 엔진 전체와 Node.js 런타임**을 통째로 번들링합니다. 이 때문에 번들 크기만 100MB를 훌쩍 넘기고, 아무것도 안 해도 기본 메모리를 수백 MB씩 점유합니다. 시스템 자원을 아끼려고 켜두는 앱이 자원을 가장 많이 먹는 주객전도 상황이 발생하는 것이죠.

### 왜 Tauri v2인가?

1. **초경량 번들 & 극소 메모리**:  
   Tauri는 브라우저를 번들링하지 않고, OS에 이미 내장된 웹뷰(macOS의 경우 `WKWebView`)를 그대로 활용합니다. 백엔드 역시 C/C++ 수준의 성능을 내는 컴파일 언어인 Rust로 빌드되므로, 번들 크기가 수 MB 단위로 줄어들고 메모리 점유율도 매우 낮습니다.
2. **macOS 네이티브 조작과 FFI (Foreign Function Interface)**:  
   맥북의 IOKit(배터리, 슬립 방지)이나 시스템 커널 API를 제어하려면 저수준 바인딩이 필요합니다. Rust는 C ABI 호환성을 갖추고 있어 macOS의 C/Objective-C 네이티브 라이브러리를 안전하고 직렬화 오버헤드 없이 호출하기에 최적이었습니다.

## 3. 웹 개발자가 이해한 데스크톱 앱: 닮은 점과 신선했던 점

서버 관점에서만 시스템을 보다가 데스크톱 앱 환경으로 넘어오니, 생각보다 웹/백엔드 아키텍처와 비슷한 점도 많았고 반대로 완전히 색다른 경험도 있었습니다.

### 비슷했던 점: 추상화 계층과 직렬화

백엔드 서버를 개발하다 보면 운영체제마다 서로 다른 비동기 네트워크 I/O 멀티플렉싱 인터페이스(`Linux: epoll`, `macOS/BSD: kqueue`, `Windows: iocp`)를 접하게 됩니다. Netty나 Go 런타임은 이를 깔끔하게 추상화하여 개발자에게 일관된 네트워크 인터페이스를 제공해 줍니다.

Tauri 역시 마찬가지였습니다. Windows, macOS, Linux의 서로 다른 창 제어, 파일 시스템, 시스템 트레이, 알림 API들을 Rust 레벨에서 단일 인터페이스로 추상화해 줍니다. 

또한 프론트엔드(JS/TS)와 백엔드(Rust)가 데이터를 주고받을 때 Rust 진영의 표준 직렬화 라이브러리인 `serde`를 사용합니다. HTTP JSON 통신을 다루듯 Rust 구조체에 `#[derive(Serialize, Deserialize)]`만 붙이면 웹뷰와 자연스럽게 통신할 수 있어 백엔드 개발자 입장에서 진입 장벽이 낮았습니다.

### 색다른 점: 마우스로 창을 끌고 다닌다고? (`data-tauri-drag-region`)

일반적인 브라우저 웹페이지는 브라우저 창이라는 샌드박스 내부의 사각형 영역 안에서만 렌더링됩니다. 웹 안의 DOM 엘리먼트를 드래그한다고 해서 컴퓨터 모니터 위에 떠 있는 브라우저 창 자체가 움직이지는 않죠.

하지만 데스크톱 앱의 커스텀 타이틀바나 트레이 팝업에서는 **"웹 화면의 특정 영역을 마우스로 잡고 끌면 OS 네이티브 창 전체가 움직여야"** 합니다.

처음엔 "마우스 드래그 좌표(`mousemove`)를 일일이 계산해서 백엔드로 IPC를 쏴 창 위치(`set_position`)를 갱신해야 하나?" 싶었습니다. 그렇게 구현하면 IPC 레이턴시 때문에 창이 덜덜 떨리며 버벅이게 됩니다.

Tauri는 이를 아주 우아하게 해결해 두었습니다.

```html
<!-- Svelte 컴포넌트 내부 -->
<div data-tauri-drag-region class="titlebar">
  <span>Zenith Dashboard</span>
</div>
```

HTML 요소에 `data-tauri-drag-region` 속성을 붙여두면, 웹뷰 엔진 레벨에서 `mousedown` 이벤트를 가로채 운영체제의 네이티브 윈도우 드래그 API(macOS의 경우 `NSWindow.performWindowDrag`)로 즉시 연결해 줍니다. 웹 기술로 만든 UI인데도 네이티브 앱과 똑같은 120Hz의 부드러움으로 창이 움직이는 걸 보며 감탄했습니다.

## 4. Tauri IPC 통신 모델 완벽 정리 (invoke, event, channel)

Tauri는 UI를 렌더링하는 프론트엔드 프로세스(Webkit)와 비즈니스 로직을 수행하는 백엔드 프로세스(Rust)가 분리된 멀티프로세스 구조입니다. 

두 프로세스 사이의 안전한 통신(IPC)을 위해 Tauri는 크게 3가지 통신 방식을 제공합니다. 백엔드 통신 패턴에 빗대어 보면 이해하기 쉽습니다.

```text
[ Tauri IPC 3가지 통신 패턴 ]

1. invoke   (HTTP Request-Response)
   Webview ──[ Command + Args ]──► Rust (tokio 비동기 태스크)
   Webview ◄──[ Return Value ]─── Rust (JS Promise로 반환)

2. event    (Pub/Sub Message Bus)
   Rust    ──[ Emit: "system-tray-click" ]──► All Listeners
   (누가 듣든 상관없이 단방향 브로드캐스트)

3. channel  (gRPC / SSE Streaming)
   Webview ──[ Start Scan ]───────► Rust
   Webview ◄──[ Chunk 1: 10% ]───── Rust
   Webview ◄──[ Chunk 2: 45% ]───── Rust
   Webview ◄──[ Chunk 3: 100% ]──── Rust
```

### 1) `invoke`: RPC / HTTP 호출 방식

가장 기본이 되는 요청-응답(Request-Response) 패턴입니다. 웹 개발 시 `fetch()`로 REST API를 호출하고 결과를 받아오는 감각과 동일합니다.

```rust
// src-tauri/src/commands.rs (Rust)
#[tauri::command]
pub async fn get_system_metrics() -> Result<SystemMetrics, String> {
    // 백그라운드에서 CPU/메모리 수집
    Ok(metrics)
}
```

```typescript
// src/lib/api.ts (Frontend TS)
import { invoke } from "@tauri-apps/api/core";

const metrics = await invoke<SystemMetrics>("get_system_metrics");
```

> **Q. Rust가 결과를 반환하는데 프론트엔드에서는 왜 `Promise`로 반환될까요?**  
> 프론트와 백엔드는 서로 다른 프로세스 메모리 공간에 존재합니다. 동기(Synchronous) C 함수를 직접 호출하는 것이 아니라, 브라우저의 메시지 채널을 통해 직렬화된 JSON 페이로드를 전달하고 결과를 비동기로 기다려야 합니다. 따라서 자바스크립트 런타임 입장에서는 `Promise`로 감싸져서 반환되는 것이 당연하며, 덕분에 UI 블로킹 없이 `async/await`로 깔끔하게 처리할 수 있습니다.

### 2) `event`: Pub/Sub 이벤트 버스

MSA 환경에서 컴포넌트 간 결합도를 낮추기 위해 Kafka나 NATS, Redis Pub/Sub을 쓰는 것과 같습니다. 수신자가 누구인지 상관없이 Rust나 JS가 이벤트를 쏘아 올리고(`emit`), 등록된 리스너가 이를 비동기 수신합니다.

- **주요 사용처**: 시스템 트레이 아이콘 클릭 감지, 창 포커스 인/아웃, 전역 단축키 눌림, 전원 플러그 연결/해제 감지 등

### 3) `channel`: 대용량 스트리밍 IPC (Tauri v2의 킬러 기능)

과거 Tauri v1에서는 디스크 전체를 스캔할 때 수만 개의 파일 정보를 전역 `event`로 연달아 쏘아 올리곤 했습니다. 이 경우 이벤트 버스에 부하가 걸려 UI가 멈칫거리는 현상이 발생했습니다.

Tauri v2에서 도입된 `channel`은 gRPC Server Streaming이나 Server-Sent Events(SSE)처럼, **단일 요청 컨텍스트 안에서 데이터를 청크 단위로 지속 스트리밍**합니다.

```rust
// Rust: 디스크 스캔 결과를 채널로 실시간 스트리밍
#[tauri::command]
pub async fn scan_storage(on_progress: tauri::ipc::Channel<ScanProgress>) -> Result<(), String> {
    tokio::task::spawn_blocking(move || {
        for (scanned, file) in find_heavy_artifacts() {
            on_progress.send(ScanProgress { scanned, file }).unwrap();
        }
    });
    Ok(())
}
```

Zenith에서는 수십 기가의 디스크 아티팩트를 스캔할 때 이 `channel`을 사용했습니다. 스캔 루프가 도는 동안 프론트엔드는 단 하나의 프레임 드랍도 없이 60fps로 실시간 프로그레스 바와 발견된 파일 목록을 부드럽게 렌더링할 수 있었습니다.

## 5. 실행 모델과 동시성: 메인 스레드를 절대 멈추지 마라

안드로이드나 iOS, 데스크톱 GUI 개발의 절대적인 제1원칙은 **"메인 UI 스레드에서 무거운 작업이나 동기 I/O를 수행하지 않는다"**입니다. 메인 스레드가 블로킹되면 사용자의 클릭이나 마우스 호버 반응이 멈추고 OS는 즉시 '무응답(ANR / Spin Dump)' 상태로 판단해 무지개 바람개비를 띄웁니다.

Tauri는 이를 해결하기 위해 Rust의 비동기 런타임인 **`tokio`**를 백엔드에 기본 탑재하고 있습니다.

- **UI Thread (Webview)**: 화면 렌더링 및 사용자 인터랙션 전담
- **Tauri Main Thread**: 윈도우 이벤트 루프 및 OS 메시지 디스패치
- **Tokio Worker Pool**: CPU 집약적 연산, 디스크 I/O, 시스템 메트릭 폴링

특히 디스크 파일 탐색처럼 동기 블로킹 I/O가 불가피한 작업은 `tokio::task::spawn_blocking`을 이용해 전용 블로킹 스레드 풀로 격리했습니다. 백엔드에서 비동기 웹서버를 다룰 때 무거운 DB 쿼리나 파일 암호화를 별도 스레드로 분리하던 테크닉과 완전히 똑같았습니다.

## 6. 백엔드 개발자 눈에 비친 안전성: TOCTOU 방어와 심링크 트랩

시스템 청소 앱의 가장 무서운 점은 **"사용자의 중요한 파일을 실수로 지워버리는 것"**입니다. 데스크톱 앱을 개발하면서 파일 시스템 보안에 대해 깊이 고민하게 된 두 가지 핵심 개념이 있었습니다.

### 1) TOCTOU (Time-of-Check to Time-of-Use) 방어

보안 분야의 고전적인 취약점인 **TOCTOU**는 **"상태를 검사한 시점(Check)과 실제로 자원을 사용하는 시점(Use) 사이에 시간차가 존재하여 그 사이에 상태가 변조되는 문제"**를 말합니다.

```text
[ 일반적인 취약한 삭제 흐름 ]
1. [12:00:00 - Scan]  /tmp/cache/build.log (크기 500MB, 안전한 파일 확인)
2. [12:00:05 - Wait]  사용자가 화면에서 검토 후 '정리하기' 버튼 클릭 대기
3. [12:00:06 - Race]  그 사이 악성 프로세스나 외부 요인이 build.log를 /etc/hosts 심링크로 바꿔치기
4. [12:00:07 - Delete] 앱이 무심코 /tmp/cache/build.log 경로를 삭제 -> 실제로는 /etc/hosts 가 삭제됨!
```

웹 백엔드에서도 프론트엔드가 보낸 금액이나 권한 데이터를 무조건 믿지 않고 트랜잭션 시점에 DB 레코드 버전과 상태를 재검증하듯, Zenith 역시 **Zero-Trust UI 원칙**으로 구현했습니다.

1. **스캔 시점**: 파일의 경로뿐 아니라 파일 시스템 고유 식별자인 **Inode 번호**, 디바이스 ID, 파일 크기, 최종 수정 시각을 메타데이터로 백엔드 메모리에 기록합니다.
2. **삭제 시점**: 사용자가 삭제를 요청하면, 경로를 바로 삭제하지 않고 디스크의 파일 메타데이터를 다시 읽어(stat) 스캔 시점의 Inode와 디바이스 ID가 정확히 일치하는지 재검증합니다. 파일이 그사이 다른 파일로 대체되었거나 변조되었다면 즉시 삭제를 거부합니다.

> **용어 짚고 가기: Inode(아이노드)란?**  
> 파일의 이름이나 경로는 파일 시스템에서 사람이 알아보기 쉽게 붙여둔 '껍데기(디렉터리 엔트리)'에 불과합니다. 실제 디스크 상에서 파일의 고유 식별자, 크기, 권한, 실제 데이터 블록의 위치 정보를 담고 있는 핵심 식별자가 바로 Inode 번호입니다. 파일 이름이 같더라도 파일이 교체되면 Inode 번호가 달라지므로 위변조를 판별할 수 있습니다.

### 2) 심링크(Symbolic Link) 트랩 방어

또 하나의 복병은 **심링크(Symlink)**였습니다. 심링크는 다른 파일이나 디렉터리를 가리키는 바로가기 포인터입니다.

만약 프로젝트 캐시 폴더를 재귀적으로 순회하며 청소(`remove_dir_all`)하는데, 누군가 그 안에 자신의 홈 디렉터리(`~`)나 루트 디렉터리(`/`)를 가리키는 심링크를 만들어 두었다면 어떻게 될까요? 

재귀 탐색기가 심링크 포인터를 무심코 따라가 버리면(dereference), 캐시만 지우려다 사용자 문서와 시스템 전체를 깨끗하게 지워버리는 끔찍한 대참사(Symlink Directory Traversal Trap)가 일어납니다.

이를 방지하기 위해:
- 심링크를 따라가지 않는 `symlink_metadata()`(Unix의 `lstat`)를 사용하여 파일 타입을 엄격히 검사했습니다.
- 대상이 디렉터리 심링크인 경우 내부를 파고들지 않고 심링크 파일 자체만 안전하게 해제하도록 방어 로직을 작성했습니다.

### 3) Rust의 RAII로 메모리/핸들 누수 원천 차단

Go 언어로 데스크톱 백그라운드 앱을 만들었을 때는 실수로 파일 디스크립터를 닫지 않거나, 취소 채널을 닫지 않아 고루틴이 백그라운드에서 좀비처럼 살아남는 메모리 누수를 겪은 적이 있습니다.

반면 Rust는 **RAII (Resource Acquisition Is Initialization)** 패턴이 언어의 뼈대에 내장되어 있습니다. 메모리 할당, 파일 핸들, 윈도우 이벤트 리스너 등 모든 자원의 생명주기가 변수의 스코프와 소유권에 바인딩되어 스코프를 벗어나는 즉시 `Drop` 트레이트가 호출되어 안전하게 정리됩니다. 맥북 메뉴바에 며칠 동안 계속 상주시켜 두어도 메모리가 단 1MB도 새지 않는 견고함을 체감할 수 있었습니다.

## 8. AI 에이전트와 페어 프로그래밍한 소회

솔직히 고백하자면, 백엔드 개발자인 제가 짧은 시간 안에 익숙지 않은 macOS 시스템 커널 API와 Rust Tauri v2의 신규 스펙을 모두 섭렵해서 앱을 완성할 수는 없었을 것입니다. 

개발 과정의 많은 보일러플레이트 코드와 플랫폼 네이티브 바인딩은 AI 에이전트와 페어 프로그래밍을 하며 작성했습니다.

하지만 AI를 쓸 때 가장 위험한 순간은 **"AI가 짠 코드를 이해하지 못한 채 무지성으로 Merge할 때"**입니다. 특히 데스크톱 앱처럼 사용자 로컬 디스크에 직접 쓰기/삭제 권한을 행사하는 앱에서는 한 줄의 버그가 치명적일 수 있습니다.

그래서 저는 AI가 만들어준 코드 변경점(Diff)을 검증할 때 `/explain-diff` 같은 워크플로우를 적극 활용했습니다.

- "이 FFI 함수 호출에서 메모리 할당 해제가 보장되는가?"
- "파일을 삭제할 때 발생할 수 있는 Race Condition은 없는가?"
- "Tauri 커맨드의 인자 검증이 빠져있지 않은가?"

AI에게 구현을 맡기되, **설계와 보안 검증, 그리고 아키텍처의 빈틈을 메우는 것은 오롯이 개발자의 몫**이었습니다. 덕분에 개발 속도는 몇 배로 끌어올리면서도 코드베이스 전체를 완벽히 장악한 상태로 프로젝트를 완주할 수 있었습니다.

## 9. 마치며

처음에는 "맥북 청소 스크립트 돌리기 귀찮다"는 아주 단순하고 게으른 이유로 시작한 사이드 프로젝트였습니다. 

하지만 직접 밑바닥부터 만들어보면서:
- 브라우저 뒤에 숨겨진 윈도우 시스템과 IPC 메커니즘을 이해할 수 있었고,
- 시스템 프로그래밍 레벨에서의 보안(TOCTOU, 심링크 방어)을 체득했으며,
- 백엔드 개발자로서의 지식(비동기 런타임, 직렬화, Zero-Trust 모델)이 데스크톱 환경에서도 고스란히 유효하다는 즐거운 깨달음을 얻었습니다.

아직 개인적인 니즈에 맞춘 기능 위주이고 다듬어야 할 사소한 부분들도 남아 있지만, 매일 내가 만든 도구로 내 맥북을 쾌적하게 관리하는 경험은 개발자로서 오랜만에 느껴보는 순수한 재미였습니다. 

혹시 맥북 용량 부족과 넘쳐나는 개발 아티팩트로 고민하고 계신다면, 가벼운 마음으로 직접 도구를 만들어보시는 걸 추천합니다!
